# SEO strategy for surojd.com

## Scope and measurement notes

This is a search-intent and business-fit plan, not a paid keyword-tool export. The difficulty values below are **initial estimates** (Low / Medium / High), not measured KD scores; there are no search-volume claims. Validate priorities against Google Search Console, Google Keyword Planner, and a current SERP review before committing to a publishing calendar. Re-score quarterly using impressions, qualified clicks, ranking URL, inquiries, and closed work.

Use **High / Medium / Low** business value as the relative likelihood that a relevant search can produce a qualified software-development lead. The target pages are recommended destinations, not a direction to publish near-duplicate doorway pages. Combine overlapping phrases on one useful page and only create a location or technology landing page when it has distinct, verifiable experience and useful content.

The live profile identifies Suroj as based in Khokana, Lalitpur, Nepal and available to work worldwide. Local recommendations below reflect that; do not imply offices or service areas that do not exist.

## 1. SEO audit strategy for Astro

### Current implementation and first fixes

- Set Astro's `site` to the live canonical origin, `https://surojd.com`; the prior `.com.np` value made generated canonicals and sitemap URLs disagree with the live site.
- Use one shared metadata component for title, unique description, absolute canonical, Open Graph, Twitter cards, and page-level `noindex`. The new `src/components/SEO.astro` and `src/components/Schema.astro` provide that shared layer, used by `src/layouts/Layout.astro`.
- `@astrojs/sitemap` already generates `sitemap-index.xml` at build time. `public/robots.txt` now advertises it. Do not submit a sitemap containing staging, duplicate, or intentionally noindexed URLs.
- Each current page has a canonical based on its public path. Prefer relative paths in page props; the component resolves them to the configured `site` origin. Ensure the preferred `www`/non-`www`, HTTPS, and trailing-slash behavior is enforced by the production host with one-hop redirects.
- Remove the obsolete `meta keywords` tag: major search engines do not use it for ranking. Avoid duplicating robots directives; the SEO component is the source of page-level indexability.
- The homepage presently consists largely of portfolio sections. Treat `/services/`, `/case-studies/`, `/blog/`, and `/contact/` as planned information architecture, not URLs to expose until each has useful, finished content.
- Review the existing 404 response: it must return HTTP 404, and its HTML should say `noindex, follow`; do not put it in the sitemap.
- Do not publish empty RSS feeds, taxonomy archives, or tag pages. Add them when there are posts worth discovering.

### Metadata and dynamic page metadata

- Give every indexable page a distinct title (usually 50–60 characters as a drafting guide, not a hard Google limit) and a compelling, accurate description (roughly 140–160 characters as a drafting guide).
- Use one clear H1 matching the page's actual purpose; write helpful visible copy rather than relying on metadata alone.
- For content/project detail pages, derive title and description from validated frontmatter. Add per-page overrides where autogenerated titles would be repetitive.
- Canonicalize only true duplicates to the preferred equivalent. Do not canonicalize a service page to the homepage merely because it is short.
- Never use a keyword dump in titles/descriptions. Avoid stuffing `meta keywords`; Google ignores it.

### Open Graph, Twitter, and images

- Set `og:title`, `og:description`, `og:type`, `og:url`, `og:site_name`, `og:image`, and meaningful image alt text. Set Twitter `summary_large_image`, title, description, and image consistently.
- Use an absolute, crawlable, social-platform-compatible raster image (ideally 1200 × 630) with readable branding and no tiny text. A 400 × 400 profile image is not an ideal large card. Check the generated URL, status, dimensions, and social debugger previews after deployment.
- Generate one OG image per statically rendered route when content volume justifies it; cache/build it once, not on each request. The build-time pattern is in section 6.

### Crawling, sitemap, RSS, and robots

- `@astrojs/sitemap` discovers generated pages from Astro's route manifest. Build with the production `site` URL, then inspect `dist/sitemap-index.xml` and each child sitemap for correct canonical origins and accidental pages.
- Keep `robots.txt` permissive for public content and include the absolute sitemap-index URL. `robots.txt` is not a privacy mechanism and should not block CSS, JS, or images needed for rendering.
- A sitemap helps discovery; it does not make a URL indexable. Only include canonical, 200-response pages. Remove thin, duplicate, redirecting, or noindex URLs.
- For a real blog, create `/rss.xml` from the same published collection, with absolute item URLs and stable publication dates. Link it with `<link rel="alternate" type="application/rss+xml" ...>`; do not create an empty feed before publishing.
- Use crawlable `<a href>` links for navigation, breadcrumbs, pagination, and contextual links. Do not depend on client-side fetches to add substantive page content after load.

### Structured data and breadcrumbs

- Use JSON-LD generated from the same validated content used to render the page. The shared `Schema.astro` safely serializes JSON-LD; page-specific schemas should be passed in only when accurate.
- Good fits: `Person` for an individual consultant, `WebSite`, `BreadcrumbList`, and `Article` for a genuine authored article. Add `Service` only to a real service detail page. Never invent reviews, ratings, awards, prices, employment, or a business address.
- A person-based freelancer should not mark themselves up as a multi-office `LocalBusiness` without a qualifying real-world business location. A factual postal address can be omitted if privacy or accuracy is a concern.
- Add visible breadcrumbs to nested pages and matching `BreadcrumbList` JSON-LD. Validate with Google's Rich Results Test and Schema Markup Validator; structured data does not guarantee a rich result.

### Performance and Core Web Vitals

- Measure mobile CrUX/PageSpeed Insights and real-user data, then fix the largest actual LCP and INP issues first. Do not equate a green lab score with improved rankings.
- Keep SSG for public content; minimize client JavaScript, third-party tags, and above-the-fold image work. Reserve image width/height, provide responsive formats, compress media, and lazy-load only below-the-fold images.
- Audit the existing deferred Google Tag Manager loader and all tags it loads; remove unused tags and measure their effect. Avoid preconnecting to hosts that are not needed on the page.
- Use semantic headings, visible focus states, useful alt text, sufficient contrast, and responsive layouts. These improve accessibility and usability as well as rendering robustness.

## 6. Astro-specific implementation patterns

The project is Astro 5. **Astro does not use Next.js `generateStaticParams()`**. Use `getStaticPaths()` for dynamic route prerendering. Astro content collections should be validated with schemas and queried at build time. The snippets are patterns to adapt to the deployed versions; keep the currently working site configuration and test the production build after each integration change.

### Content Collections and dynamic static routes

Example schema for a future article collection using the Astro 5 glob loader:

```ts
// src/content.config.ts
import { defineCollection, z } from 'astro:content';
import { glob } from 'astro/loaders';

const blog = defineCollection({
	loader: glob({ base: './src/content/blog', pattern: '**/*.{md,mdx}' }),
	schema: z.object({
		title: z.string().min(1),
		description: z.string().min(50).max(200),
		pubDate: z.coerce.date(),
		updatedDate: z.coerce.date().optional(),
		author: z.string().default('Suroj Dangol'),
		draft: z.boolean().default(false),
		category: z.enum([
			'Java',
			'Spring Boot',
			'React',
			'Flutter',
			'AWS',
			'SaaS',
			'WordPress',
			'VPS',
			'Linux',
			'Payments',
		]),
		tags: z.array(z.string()).default([]),
		image: z.string().optional(),
	}),
});

export const collections = { blog };
```

Then filter drafts and produce static article paths:

```astro
---
import { getCollection, render } from 'astro:content';
import Layout from '@layouts/Layout.astro';

export async function getStaticPaths() {
	const posts = await getCollection('blog', ({ data }) => !data.draft);
	return posts.map((post) => ({ params: { slug: post.id }, props: { post } }));
}

const { post } = Astro.props;
const { Content } = await render(post);
---

<Layout
	title={post.data.title}
	meta={{
		title: `${post.data.title} | Suroj Dangol`,
		description: post.data.description,
		url: `/blog/${post.id}/`,
		image: post.data.image,
	}}
>
	<article>
		<h1>{post.data.title}</h1>
		<p>Published <time datetime={post.data.pubDate.toISOString()}>{post.data.pubDate.toLocaleDateString('en')}</time></p>
		<Content />
	</article>
</Layout>
```

If using a different Astro 5 minor version, confirm `glob()` and `render()` signatures against that installed version. Do not retrofit the existing projects collection without migrating its content and checking existing project routes.

import { getCollection } from 'astro:content';

### Automatic Open Graph image generation

Use a build-time endpoint and a pinned renderer (for example `satori` plus `sharp`) only after adding those dependencies intentionally. Astro static endpoints must enumerate paths with `getStaticPaths()`; no request-time server is required for SSG. A route can render an SVG template using escaped frontmatter and convert it to PNG with Sharp. Then set each page's `image` metadata to its generated `/og/{slug}.png`. Escape XML characters before interpolating user-authored titles; test the output dimensions, content type, and final generated files. Avoid relying on `generateStaticParams()` or assuming an Astro endpoint is dynamic on a static host.

Example endpoint contract (the renderer function and its dependencies should be implemented and pinned in the actual project before use):

```ts
// src/pages/og/[slug].png.ts — static route pattern
export async function getStaticPaths() {
	const posts = await getCollection('blog', ({ data }) => !data.draft);
	return posts.map((post) => ({
		params: { slug: post.id },
		props: { title: post.data.title },
	}));
}

export async function GET({ props }: { props: { title: string } }) {
	const png = await renderOgPng(props.title); // deterministic SVG + raster conversion
	return new Response(png, {
		headers: { 'Content-Type': 'image/png', 'Cache-Control': 'public, max-age=31536000, immutable' },
	});
}
```

The endpoint is intentionally a contract, not copy/paste production code: `renderOgPng` must be supplied by a real, pinned renderer, and the `getCollection` import is required in its module. Do not ship a stub or advertise a generated image URL that is absent from `dist/`.
